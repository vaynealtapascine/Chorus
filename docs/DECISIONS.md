## Architecture

| ID | Decision | Source |
| --- | --- | --- |
| D-030 | Server: **Rust** (axum + tokio) with **SQLite** (WAL) via rusqlite. Single binary. | Owner |
| D-031 | Web: **Svelte 5 + Vite + TypeScript PWA**, offline-capable, local store in IndexedDB, syncs on reconnect. | Owner |
| D-032 | Android: **native Kotlin + Jetpack Compose**, Room over SQLCipher, Glance widgets, WorkManager. | Owner |
| D-033 | Transport: server reachable only on the tailnet via Caddy (TLS). Encryption at rest **on devices** (SQLCipher, Keystore); no E2E. | Owner |
| D-034 | Auth: **invite link + per-device keypair** (challenge/response), revocable sessions, no passwords. Optional Tailscale identity check as second factor (Advanced). | Owner |
| D-035 | Push: **UnifiedPush via self-hosted ntfy** on the tailnet. Fallback: foreground WebSocket service (opt-in), then WorkManager polling. | Owner |
| D-036 | Data is an **append-only op log** (event-sourced) + **projected tables** that are plain, readable SQL. Projections are rebuildable from the log. | Spec |
| D-037 | Conflicts on switches: **merge by real time**; both kept; current = latest; overlapping independent switches within the review window (default 2 min) produce a gentle **review card**, never a silent drop. | Owner |
| D-038 | Timestamps: device wall time + HLC; server measures per-device clock offset and stores raw + corrected time. | Owner |
| D-039 | Offline-sent messages appear at their **original time** with a "sent offline · synced HH:MM" marker; unread counts still bump. | Owner |
| D-040 | Shared logic lives in `chorus-core` (pure Rust) → native on server, **UniFFI** on Android, **wasm-bindgen** on web. Spike in M1.10; fallback is Kotlin/TS ports gated by the same conformance fixtures. | Spec |
| D-041 | Rich text stored as **plain text + entity ranges** (Telegram model), not markdown. The plain `text` column is directly analysable. | Spec |
| D-042 | IDs are **UUIDv7** as lowercase TEXT; times are **INTEGER milliseconds UTC** in columns ending `_at`, plus `tz_offset_min` where local time matters. | Spec |
| D-043 | Backups: nightly SQLite snapshots with rotation (keep N), phone keeps a full replica of the owner's own system, export on demand. No offsite in v1. | Owner |
| D-044 | Repo: `source/repos/Chorus`, public GitHub, MIT, owner's house README standard. | Owner |
| D-055 | Snapshots/catch-up are **op pages**, not table rows: every device is an op replica for its scopes (needed for `reproject` and for restoring a server). Table-row snapshots may be added later as an optimization. | Spec (M1.9) |
| D-056 | M1.10 spike **kept** the shared-core plan: `chorus-ffi` (UniFFI 0.32, JSON-string API over `chorus_core::api`) builds for arm64-v8a (0.96 MB) and x86_64; Kotlin bindings generate in library mode; `chorus-wasm` builds, runs in Node, 209 KB gzipped without wasm-opt (budget 300 KB). The on-device call is verified in M0.3. | Spec (M1.10) |
| D-057 | After a server restore, a **restore window** lets devices re-push ops with their original author and times (SYNC.md §7.3); it is closed by the admin with `chorus-server reconcile-close`. Outside it, pushes are always stamped as the pusher's. | Spec (M1.9) |
| D-058 | The quick-switch widget uses plain **RemoteViews** (`AppWidgetProvider` + `RemoteViewsService` grid), not Glance: no extra dependency (dl.google.com was unreachable for builds), full control over redraw cost, and the same behaviour as CLIENTS.md §3. Mode, per-widget folder and the last switch for Undo live in SharedPreferences so taps work in a cold process. Pins are not implemented yet (recents lead the grid). | claude-opus-5.5 (M4.5) |
| D-059 | Android push uses the **UnifiedPush connector protocol directly** (a few broadcasts: REGISTER / NEW_ENDPOINT / MESSAGE / MESSAGE_ACK) instead of the `org.unifiedpush.android:connector` library, which can't be fetched offline; the distributor is the ntfy app pointed at the owner's ntfy. Payloads are RFC 8291 `aes128gcm`; server (Rust) and app (JVM) are both tested against the RFC's published example. | claude-opus-5.5 (M8.1) |
| D-060 | In-app updates (M12.3): the server serves `app/android/chorus.apk` + `chorus.json` (`GET /api/v1/android/latest`, `/download/android`), published by `deploy.ps1 -Android`. `versionCode` = git commit count. Release APKs are signed with this PC's Android debug key (`~/.android/debug.keystore`) so every build upgrades in place; a proper release key can replace it later only by reinstalling once. The app checks every 12 h on unmetered networks, verifies sha256, installs via PackageInstaller (silent on Android 12+ once Chorus installed itself, else a one-tap notification). | claude-opus-5.5 (M12.3) |
| D-061 | **Web Push for the PWA (L6, pulled forward)**:<br>• A browser subscribes with the server's VAPID key (`GET /api/v1/push/vapid`; the key is made on first use and kept in `server_meta`) and registers like an Android device (`PUT /devices/push`).<br>• Pushes to `platform = 'web'` devices carry an RFC 8292 VAPID header. The `sub` is `server.public_url` if it is https, else `mailto:chorus@localhost`. UnifiedPush endpoints get no header, because ntfy treats `Authorization` as its own auth.<br>• The payload is the same RFC 8291 ciphertext, but it travels through the browser vendor's push service (Google, Mozilla or Apple), outside the tailnet. Those services see timing and size, never content. It is opt-in per browser ("Notify me in this browser"). | claude-opus-5.5 (L6); confirmed by the owner 2026-09-23 (was Q13) |
| D-062 | **Linux / public VPS deployment** alongside the Windows PC one (owner request 2026-09-24). Supersedes D-033's "reachable only on the tailnet" for such installs; the PC install stays tailnet-only.<br>• `scripts/pack-linux.ps1` builds a static x86_64 musl `chorus-server` in the `rust:1.98` image (Docker under WSL), bundles the web app, Android update files and `deploy/linux/install.sh`, optionally with a verified data snapshot (`-WithData`).<br>• `install.sh` (Debian 12+/Ubuntu 22.04+): a `chorus` service user, `/opt/chorus/{app,data,backups}`, `/etc/chorus/chorus.toml`, a sandboxed systemd unit, Caddy with the site in `/etc/caddy/sites/chorus.caddy` (imported, not a rewritten Caddyfile), imports through the normal restore path (epoch bump → devices re-send).<br>• Being public changes the threat model: `security.webhook_targets` (`internal` default with loopback now refused, `public` on the VPS, `any`); checked addresses are pinned and redirects not followed; the server stops cleanly on SIGTERM.<br>• Tested with `scripts/test-linux.ps1` (Debian 12 + systemd in Docker under WSL): install, update, import. | claude-opus-5.5 |
| D-063 | **Account settings are one `pref.set` per key** (`device: ''`), never a whole `account.settings` object, so two devices editing different settings don't clobber each other. `account.settings` stays a legacy read fallback (e.g. `follow_ceiling`, whose history/stats sharing flags live inside that pref). | gpt-6-sol (D-S2-1), accepted by claude-opus-5.5 at the batch 3 audit |
| D-064 | **Backups are snapshot directories**: `chorus-<stamp>-<rand>/` with `chorus.db` (SQLite online backup) and `manifest.json` (format 1, db sha256, blob list), blobs pooled once in `backups/blobs/` by hash. Restore verifies everything and only writes a new directory. Replaces the `.db.zst` of OPS §5 (no zstd dependency offline); compression can come later as manifest format 2. | gpt-6-sol (D-S2-2), accepted by claude-opus-5.5 |
| D-065 | **Exports are direct downloads for now**: `GET /exports/{ops.jsonl, <table>.csv, account.sqlite}` scoped to the caller's account (sessions or `export` tokens) and `chorus-server export`. The DATA_MODEL §7 zip with blobs and `POST /exports` background jobs come later; `--kind full` means the authored-op JSONL, not an importable backup. | gpt-6-sol (D-S2-3), accepted by claude-opus-5.5 |

| D-066 | **A follower's prefs stay the follower's**: `follow.set_prefs` (mute, which members, quiet hours, digest time, UTC offset) is written by the server into the *follower's* account scope, not the followed account's, so the followed system's devices never sync it and its exports don't contain it. The server's follow row still projects it (a follow is projected from all its ops). Prefs written before this change remain in those systems' op logs (D-053: no erase without `purge`). | claude-opus-5.5 (privacy fix, 2026-09-24; no visible behaviour changes) |
| D-067 | **The restore window closes by itself 7 days after a restore** (and sooner with `chorus-server reconcile-close`). While open, restore pushes keep the author, device and times they claim, and skip the private-message and follow-forgery checks; left open (it used to stay open until closed by hand, and an `install.sh --import` opens one), that is a lasting way to forge authorship on a public server. A week covers phones that were off; later restore pushes count as the pusher's own ops, so nothing is lost, only re-attributed. | claude-opus-5.5 (security fix, 2026-09-24; no visible behaviour changes) |
| D-068 | **The export bundle with files is in v1** (owner, 2026-09-24, answering Q14): the DATA_MODEL §7 "full backup" as a background job, per the remote batch R7 proposal (now in `docs/handoff/opus-remote-2.md`, appendix). The owner approved the feature, not the sub-questions, so the proposal's defaults stand: a zip, *stored* and written without a new dependency, only blobs referenced by the account's own ops, one job per account, kept 24 h. Also recorded: "desktop" in the v1 goal means the installed PWA staying usable with the server down (CLIENTS.md §4.3), not a separate desktop app. | owner / claude-opus-5.5 |
| D-069 | **Feeds that filter by fronting are shareable, with a warning** (owner, 2026-09-24, answering Q15). A shared feed using `fronting:` evaluates for a follower under that follower's ceiling (NOTIFICATIONS §3: only switches already revealed to them count, never earlier or more precisely than their notifications), and both the owner (when sharing) and the reader (when opening) see a banner that the feed reveals who was fronting when posts were written. Replaces the R10 default (owner-only, 400 for others). | owner / claude-opus-5.5 |
| D-070 | **"Keep everything on this device" (full history offline)** (owner request 2026-09-24). Devices already sync every op they may see (the SYNC §6 web window was never built), and web search is local; this makes it explicit and complete: a per-device setting, on by default for Android and the installed PWA, with a **Sync everything now** button that re-checks every scope's digest, fetches anything missing (and optionally attachments into the offline blob cache), and shows progress and space used. Offline search covers messages, posts and switches. If the setting is off, the SYNC §6 window applies. Scale target: a device with 100k ops opens in ≤ 2 s (the web replica must stop loading every op into memory at start). | owner / claude-opus-5.5 |
| D-071 | **Chorus Home: one-click self-hosting on a home PC** (owner request 2026-09-24), Windows first, beside the technical installs (D-062, OPS.md). One self-installing `chorus-server.exe` registers a `ChorusHome` Windows service (starts at boot), a private-network firewall rule and a Start-menu shortcut, and opens `http://localhost:<port>` on a setup page; settings live in a loopback-only page, not hand-edited TOML. Home wifi transport: the PC's browser uses `localhost` (a secure context); phones use the Android app over TLS with a **self-signed certificate pinned by fingerprint from the invite QR**; other browsers on the wifi are pointed to Tailscale. Home wifi only; nothing exposed to the internet. Design and build order: `docs/HOME.md`. | owner / claude-opus-5.5 |
| D-072 | **The Android release key lives in Infisical** (owner, 2026-09-25; was Q16). The owner's keystore (an existing JKS/PKCS12 packed by `scripts/pack-android-key.ps1`, or a new one from `scripts/new-android-key.ps1`) is stored as `ANDROID_SIGNING_KEY` (JSON: alias, password, key_password, base64 keystore) in the Infisical project `chorus-cec1`, keeping an offline copy. `.github/workflows/release-android.yml` signs the APK on a tag `v*` (or a manual run), reading the secret through GitHub OIDC with the machine identity `github-ci-handler`, so no key or password is stored in GitHub. It refuses a debug-signed result and publishes `Chorus-<tag>.apk` on the GitHub release beside Chorus Home. Builds on the owner's PC and the in-app updates from the owner's server keep the debug key (D-060); the owner's phone moves to the release key only if the owner chooses a one-time reinstall. | claude-opus-5.5 |
| D-073 | **Only a message's author edits it.** `manage` in a channel (and the space's owner) moderates other people's messages (delete, restore, pin) but can't edit them, or an admin could rewrite what someone said while it still showed under their name. The web already offered Edit only on your own messages; the server now refuses others' `message.edit` (`perms::write_denied`). Security default; the owner can reverse it. | claude-opus-5.5 |
| D-074 | **Autoproxy is per account, not per channel row** (R22.4). A channel's speaker default (SPEC §5.2: `off` · `front` · `latch` · `member`, the last being the "sticky speaker") is the account's pref `autoproxy:<channel id>` = `{"mode", "member"?}` (default `front`), not `channel.settings`: every account in a shared space shares the channel row, and one system's speaker choice isn't another's to see or change. `latch` keeps no state: it is the authors of the account's latest message in the channel. The rule is `chorus_core::speaker::default_speaker` (a person account always speaks as itself, D-003; a sticky member that's gone falls back to the front). | claude-opus-5.5 |
| D-075 | **A windowed replica says its window; both sides leave the same ops out** (R23). A browser tab without "keep everything" keeps the message-family ops the server *received* in the last 90 days (DATA_MODEL §5's default). Instead of remembering what it evicted, the device sends `hello.window` and the server leaves those ops out of that connection's catch-up, fan-out, repairs and digests (`sync::outside_window`, `visibility::visible_digest_in`), so digests agree with no evicted-id list and no repair loops. By received time, so something that arrived recently (even if written long ago) stays: it may be what brings it back after a restore. Older history pages in over REST. | claude-opus-5.5 |
| D-076 | **Slow mode holds a message instead of refusing it** (owner, 2026-09-26; was Q17). A channel with slow mode lets each account send one message every N seconds, counted when the server *receives* it; managers are exempt. A send that arrives too soon is answered `slow_mode` with `retry: true` and `retry_after_ms`; the device holds it (`Replica::held`), shows "Slow mode: sending in N s · Cancel", and sends it again when the wait is over (`Replica::tick`), so several messages written offline go out one per interval, in order. The person can cancel any held message before it goes (`Replica::cancel_held`); it is then deleted from the device and never sent. | owner; built by claude-opus-5.5 |
